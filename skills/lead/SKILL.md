# Lead

## 定位

这是技术负责人总调度入口。它把一段业务需求通过问答澄清为可执行的交付计划，先做需求理解、工程路由和系统设计，再进入具体服务端、管理后台、客户端、测试和 Grafana 监控配置。

默认不要直接写代码。除非用户明确说“直接实现”“方案已确认”或“继续开发”，否则先完成调度层产物并等待确认。

## 触发入口

用户出现以下说法时使用本技能：

- `lead：<需求>`
- `技术负责人模式：<需求>`
- `系统调度：<需求>`
- `总体调度：<需求>`
- “这个需求帮我从服务端、管理后台、客户端、监控整体分析”
- “先做整体系统设计，不要写代码”
- “需求到开发、测试、监控闭环”

## 核心原则

- 先问答，后设计；先设计，后开发。
- 用户不用填写长模板，由 Codex 一次只问少量关键问题。
- 调度层不绑定单个工程；只有工程路由确认后才进入具体仓库。
- 高风险点必须停下来确认：数据库、权限、计费、审核、批量变更、线上兼容、Grafana 告警策略。
- 需求分析、系统设计、服务端开发、管理后台开发、客户端开发、测试、Grafana 配置必须由不同 agent 承接。
- 全方位需求必须在知识库 `/Users/chenzhiyuan/work/doc/knowledge/lead` 下建立独立需求目录并沉淀文档。
- 多仓库任务必须分仓库验证、写 session、commit、push，不混合提交。
- 新需求进入具体工程实现前，每个涉及工程都必须先从远程 `master` 拉取新的同名分支；同一需求跨多个工程时分支名必须保持一致。
- 测试用例和监控指标必须来自系统设计，不在开发结束后临时补。
- 全流程系统设计必须能指导闭环开发：明确每个服务的北向 API、南向存储或依赖、核心流程图、黑盒集成测试计划、本机多工程启动验证方式，以及设计确认后的任务拆分规则。
- 任务规划和测试用例必须分开维护。用户确认系统设计前，不输出最终开发任务清单；确认后将任务拆成简单可验证切片，每个任务尽量只做 1 到 2 个 commit，完成一个标记一个并继续推进下一个。
- 所有开发任务完成后，再启动本机多服务黑盒集成测试；测试发现问题时，将问题归因给对应服务形成修复任务，修复提交后重复集成测试，直到阻塞问题关闭。

## Agent 分工硬规则

Lead 本身是调度 agent，只负责问答澄清、阶段编排、上下文交接、阻塞判断和总体验收，不直接包办所有阶段。

每个阶段必须使用不同 agent：

| 阶段 | Agent |
|------|-------|
| 需求分析 | 需求分析 agent |
| 系统设计 | 系统设计 agent |
| 服务端开发 | 服务端开发 agent |
| 管理后台开发 | 管理后台开发 agent |
| 客户端开发 | 客户端开发 agent |
| 测试 | 测试 agent |
| Grafana 配置 | 监控配置 agent |

执行要求：

- 不允许同一个 agent 连续兼任多个专业阶段。
- 每个 agent 只接收本阶段必要上下文、上游确认产物、验收标准和交付要求。
- 每个 agent 输出本阶段产物、验证结果、风险和交接说明。
- Lead agent 在阶段之间做质量门禁；门禁未通过时，不进入下一个 agent。
- 如果当前运行环境支持子 agent，优先实际启动独立 agent；如果工具环境暂不支持，必须明确说明限制，并以严格的独立角色上下文模拟，不得混淆职责。

## 知识库落地规则

全方位需求的调度层文档统一写入：

```text
/Users/chenzhiyuan/work/doc/knowledge/lead
```

每个需求一个目录，命名格式：

```text
YYYY-MM-DD-需求短名
```

推荐目录结构：

```text
lead/
└── YYYY-MM-DD-需求短名/
    ├── 01-requirements.md
    ├── 02-routing.md
    ├── 03-system-design.md
    ├── 04-test-plan.md
    ├── 05-grafana.md
    ├── 06-acceptance.md
    └── sessions/
```

文档职责：

- `01-requirements.md`：需求分析 agent 输出，记录需求理解、用户故事、范围边界和待确认问题。
- `02-routing.md`：Lead agent 输出，记录服务端、管理后台、客户端、Grafana、运营配置等工程路由。
- `03-system-design.md`：系统设计 agent 输出，记录整体架构、接口契约、数据流、状态流转、风险和回滚方案。
- `04-test-plan.md`：测试 agent 输出，记录黑盒测试用例、测试环境、测试结果和遗留风险。
- `05-grafana.md`：监控配置 agent 输出，记录 dashboard、panel、指标口径、告警策略和配置结果。
- `06-acceptance.md`：Lead agent 输出，记录总体验收结论、各工程 commit、验证证据和剩余风险。
- `sessions/`：记录阶段过程、重要交接和阻塞处理。

如果需求只推进到某个阶段，只创建并维护已完成阶段的文档；后续继续时复用同一个需求目录。

## 问答式启动

收到需求后，先判断信息是否足够。如果不足，用一组短问题启动，不要一次问太多。

默认第一轮问题：

1. 这是新需求、已有功能变更，还是线上问题？
2. 你希望本轮先做到哪一步：只做需求理解、做到系统设计、设计确认后继续开发，还是一路做到测试和监控？
3. 是否已有 PRD、飞书链接、会议纪要、截图或错误日志？
4. 是否已知涉及哪些工程？未知时是否允许先做工程路由识别？

如果用户已经明确答案，不重复提问，直接进入对应阶段。

## 阶段流程

### 1. 需求理解

目标：把业务输入转成稳定需求理解。

输出：

- 需求背景
- 业务目标
- 目标用户或角色
- 本期范围
- 非目标
- 核心业务规则
- 待确认问题

需要读 PRD、需求链接、会议纪要或产品评论时，优先使用 `requirements-analyst`。

### 2. 工程路由

目标：识别本需求可能涉及的工程和外部系统。

输出：

- 服务端工程：已知、候选或待确认
- 管理后台工程：已知、候选或待确认
- 客户端工程：已知、候选或待确认
- Grafana dashboard：已知、候选或待确认
- 运营配置、数据库、权限、消息、定时任务、第三方依赖影响面

如果涉及 `wmxs`、Pixel Studio、task-manager 或项目化交付，使用 `codex-workflow`。不确定项目时，先按需求线索查最小必要知识库和代码目录，仍不确定再问用户。

已知 App 工程路由：

- 神笔绘画 App：`/Users/chenzhiyuan/work/codes/wmxs/h5-magicpen`
- 装修大师国内版 App：`/Users/chenzhiyuan/work/codes/wmxs/h5-app/apps/homeai`
- 装修大师国际版 App：`/Users/chenzhiyuan/work/codes/wmxs/h5-app/apps/homeguru`

当需求文字出现“神笔绘画”“装修大师国内版”“装修大师国际版”“homeai”“homeguru”等线索时，客户端工程路由优先使用以上映射；仍涉及服务端、管理后台、配置或监控时，继续按工程路由流程补齐其他项目。

### 3. 系统设计

目标：从技术负责人视角形成整体方案。

输出：

- 总体架构和模块边界
- 每个服务的北向 API 协议，包括客户端、管理后台、内部服务和第三方/Agent 接口
- 每个服务的南向存储、外部依赖和数据归属，包括业务事实源与非事实源边界
- 核心逻辑流程图，优先使用 Mermaid 表达跨服务主流程、异常流程和状态流转
- 服务端接口、数据流、状态流转、事务和幂等
- 管理后台页面、操作、权限、异常反馈
- 客户端入口、状态展示、弱网和异常体验
- 数据库、缓存、消息、配置、灰度和回滚方案
- 日志、埋点、指标和 Grafana 监控口径
- 本机黑盒集成测试计划，包括需要启动的工程、测试数据、主流程、异常流程、后台验证、输出证据和问题回流规则
- 风险、开放问题、验证策略和设计确认后的任务拆分门禁

设计涉及重大取舍时，给出 1-3 个方案和推荐方案，等待用户确认。

### 4. 分工程执行

只有用户确认“开始实现”“按方案开发”“继续开发”后，才进入具体工程。

执行规则：

- 进入任一工程开发前，先 `git fetch origin master`，再基于 `origin/master` 创建本需求分支；多工程使用同一个分支名。
- 如果远程 `master` 不存在、当前工程不是 Git 仓库、工作区有无法安全区分的改动，必须暂停并说明原因。
- 服务端阶段：使用对应项目规则、`codex-workflow`、必要时使用 TDD 或系统化调试。
- 管理后台阶段：进入后台工程，实现页面、表单、列表、权限和联调。
- 客户端阶段：进入客户端工程，实现用户链路、状态、埋点和体验。
- 每个工程独立验证、写 session、commit、push。

### 5. Review 与测试

所有开发任务完成后，先做 review，再启动多服务黑盒测试。测试用例不和任务规划混写；测试发现的问题回流为对应服务的修复任务，修复后重复黑盒测试。

Review 输出：

- 阻塞问题
- 兼容性风险
- 权限和安全风险
- 日志、监控、测试缺口

黑盒测试输出：

- 测试环境和测试账号说明
- 主流程用例
- 异常流程用例
- 权限用例
- 边界参数用例
- 前后端联调用例
- 测试结果和遗留风险

### 6. Grafana 监控

测试通过后，再进入 Grafana 配置。

配置前先输出监控方案：

- Dashboard 名称或归属
- Panel 列表
- 指标口径
- 过滤条件
- 告警条件
- 验证方式

需要操作登录态页面时，使用 Chrome 能力。配置完成后记录 dashboard、panel、alert 和截图或关键配置说明。

## 阻塞条件

遇到以下情况暂停推进并说明原因：

- 需求目标或验收标准不清楚。
- 工程路由无法确认。
- 设计影响数据库、权限、计费、审核或线上兼容。
- 用户要求设计确认前不要写代码。
- 测试失败且修复会扩大范围。
- Grafana dashboard 或指标口径无法确认。
- 工作区已有改动无法安全区分。
