# Modulith 现状取证与领域识别

领域建设先回答“现在真实是什么”，再回答“目标应该是什么”。存量系统尤其不能只看目录名或旧设计图。

## 取证优先级

按以下顺序使用证据，并记录证据位置和时效：

1. 当前代码、数据库结构、实际接口契约、结构测试和可重复验证结果。
2. 已生效的 Spec、Validation、API、SQL、Ops 和项目级约定。
3. 当前运行环境中可安全验证的行为、日志和数据所有权。
4. 进行中的 Plan、历史提交和旧架构图。
5. 访谈描述、命名猜测和未来设想。

高优先级证据冲突时，先列出冲突，不急于把某一版包装成最终结论。

## 现状盘点

至少检查与任务直接相关的入口，不进行无边界全库扫描：

- 产品入口和 Action / Controller：业务用例从哪里进入。
- 公开 API、SDK、事件和回调：领域外实际依赖什么。
- Service、状态机、规则和定时任务：业务决策在哪里发生。
- Dao、Entity、表、缓存和对象存储索引：谁拥有数据和生命周期。
- 外部系统适配：哪些只是协议翻译，哪些承载业务语义。
- 测试和结构约束：哪些边界已经被自动化证明。
- 配置和运行态：代码是否真正接入主业务链路，是否受环境阻塞。

使用下表区分“存在”和“落地”：

| 能力 | 代码已存在 | 已接入业务链路 | 数据/契约已生效 | 已验证 | 当前结论 |
|---|---|---|---|---|---|
| 示例能力 | 是/否 | 是/否 | 是/否 | 证据 | 已落地 / 部分落地 / 仅预留 / 已阻塞 |

不能因为类、接口或包已经创建，就判断能力已完成。对于迁移任务，还要单独列出“已完成的结构改造、已验证健康的行为、仍未解决的阻塞”。

## 基本概念

| 概念 | 本技能中的含义 | 常见误判 |
|---|---|---|
| 业务域 | 围绕稳定业务目标和能力集合形成的业务范围 | 一个产品、一个代码仓库或一个组织名称 |
| 限界上下文 | 一套业务语言、模型、规则和数据所有权保持一致的边界 | 一个 Java package 就天然是一个上下文 |
| 领域能力 | 领域对外承诺的稳定业务结果 | 一个 Service 方法或 HTTP 接口 |
| 产品入口 | 面向用户或调用方组织多个领域能力的入口 | 因为有独立 APP 就必须独立成核心域 |
| 流程域 | 本身拥有稳定目标、状态和规则的跨能力流程 | 任意跨域调用都建一个“编排域” |
| 外部执行者 | 执行业务委托但不拥有本服务业务语义的系统 | Worker、任务平台或供应商被画成内部业务域 |
| 工程公共模块 | 承接技术封装或工程共享的代码组织 | `common` / `foundation` 被直接当成基础业务域 |

## 候选领域判断

对每个候选上下文逐项取证：

| 维度 | 要回答的问题 |
|---|---|
| 业务语言与目标 | 是否存在一组稳定术语和独立业务结果？同一个词在边界内外是否含义不同？ |
| 规则与不变量 | 是否有只能由该能力维护的规则、权限、幂等或一致性约束？ |
| 状态演进 | 是否有独立生命周期、状态迁移或时间有效性？没有显式状态机时，是否仍有独立规则演进？ |
| 数据所有权 | 哪些主记录、流水、配置和资产生命周期只能由它修改？ |
| 事务与失败边界 | 哪些操作必须原子完成？失败、重试、补偿由谁负责？ |
| 公开能力 | 领域外真正需要依赖的业务结果是什么？是否能用稳定契约表达？ |
| 独立演进 | 规则、发布节奏、团队认知或规模是否要求独立演进？ |

这些维度用于形成证据链，不做机械打分。简单查询型领域可能没有复杂状态机，但仍可因明确语言、规则和数据所有权形成独立边界。

## 拆分判断

出现以下信号时，优先检查一个大域是否应拆分：

- 同一个词在不同流程中含义不同，模型被大量可选字段和场景分支污染。
- 不同能力各自拥有状态、规则、表和失败恢复，只有入口或技术链路相同。
- 一个域同时承担配置定义、生产执行、资产生命周期和商业履约等不同业务目标。
- 修改一类规则总会迫使无关能力一起发布或回归。
- 上游历史格式泄漏到下游领域，接收方被迫理解发送方内部模型。
- 某个跨域流程已经形成稳定业务目标、状态和补偿责任，值得成为流程域。

## 合并判断

出现以下信号时，优先检查是否只是伪领域：

- 只有技术分层或供应商封装，没有自己的业务语言和规则。
- 数据完全属于另一个领域，只提供透传或薄包装。
- 生命周期始终与另一个领域同步，无法说明独立失败和演进边界。
- 所谓公开能力只是内部实现步骤，领域外不应直接依赖。
- 拆分后产生双向同步、共享表和大量跨域内部对象，边界成本高于业务收益。

## 常见错误裁决

- 多处复用：只能说明需要稳定契约，不能直接说明它是支撑域、基础域或独立域。
- 核心链路依赖：只能说明依赖重要，不能决定被依赖方的战略分类。
- 代码已经分包：只能作为当前实现证据，不能替代业务边界判断。
- 产品名称不同：产品可以是多个领域能力的组合入口，不必一产品一领域。
- 同一张表：可能说明历史耦合，不代表这些能力天然属于同一领域。
- 同一个外部平台：技术执行链相同，不代表上层业务语义相同。
