# 对象边界与 Javadoc 规范

## 1. 对象所有权

- 领域公开契约由能力拥有方定义。调用方只能依赖拥有方公开的 `Api / Command / Query / Result / Event` 或显式命名接口。
- `Entity / Aggregate / DO / Mapper / Repository / Dao` 和内部 DTO 属于领域内部实现，不得跨域引用。
- Controller 的 `Req / Resp` 属于传输边界；进入应用层前转换为领域命令或查询，不能沿调用链传入其他领域。
- 外部 SDK、供应商响应、消息原文和历史协议对象在基础设施边界转换，领域模型不得直接理解外部字段语义。
- 跨域对象只携带完成协作所需的稳定语义；不要为了少写转换而暴露整张表、聚合内部状态或可变集合。

## 2. 公开对象最小集合

| 对象 | 用途 | 约束 |
| --- | --- | --- |
| `*Api` | 同步公开能力 | 由能力拥有方定义；方法名使用业务语言 |
| `*Command` | 请求发生状态变化 | 表达意图，不暴露调用方流程细节 |
| `*Query` | 请求读取信息 | 查询条件与分页、时间范围语义明确 |
| `*Result` | 返回稳定业务结果 | 不直接返回 Entity、DO 或供应商对象 |
| `*Event` | 告知已经发生的业务事实 | 使用过去式语义，携带事件标识和发生时间 |

仅当多个调用方确实需要同一组稳定能力时，才创建命名接口子包。不要把 `internal` 整包改成开放面。

## 3. 完整 Javadoc 门槛

新增或修改的 Java 代码默认使用中文 Javadoc，并满足下列要求：

### 3.1 包与类型

- 每个领域根包的 `package-info.java` 说明领域目标、公开面和依赖边界。
- 每个 `@NamedInterface` 包说明开放原因、可被谁使用，以及不保证开放的内部内容。
- 所有公开类型必须有 Javadoc，包括接口、抽象类、枚举、注解、记录和异常。
- `Api / Command / Query / Result / Req / Resp / DTO / Event / Payload / Config / Rule / Policy / Context / Entity / DO` 等业务对象必须有类型说明。
- 类型说明应讲清业务角色、所属边界和关键不变量；不能只写“某某类”“请求参数”“返回对象”。

### 3.2 POJO 与业务字段

- POJO 的每个业务字段和 record component 都必须说明业务含义。
- 有单位的字段写明单位；时间字段写明时区或时间口径；金额写明币种和精度；比例写明取值范围。
- 可空字段写明何时为空；枚举或状态字段写明有效状态及状态来源；ID 写明所标识的业务对象。
- 集合字段写明是否有序、是否允许重复、空集合与 `null` 的差异。
- 不因 Lombok 生成 getter/setter 就省略字段 Javadoc；字段是业务契约的一部分。

### 3.3 方法、参数与返回值

- 暴露 API 的所有方法、接口方法以及核心 application/domain 方法必须有 Javadoc。
- 公开或受保护的构造方法必须有 Javadoc，并为每个构造参数声明 `@param`。
- 每个参数都必须有对应的 `@param`，说明业务含义、格式、范围、空值和默认行为；不能只复述参数名。
- 非 `void` 方法必须有 `@return`，说明结果语义、空值/空集合和失败时行为。
- 声明的业务异常必须有 `@throws`，说明触发条件；不要记录实现上永远不会抛出的异常。
- 核心方法需补充业务目标、前置条件、不变量、事务边界、幂等键、副作用和部分失败处理。只写其中与该方法真实相关的内容。
- 重写方法仅在语义完全不变且目标项目允许时使用 `{@inheritDoc}`；若增加业务规则、失败条件或副作用，必须补充自己的 Javadoc。

### 3.4 公开 API 特别要求

公开 API 的 Javadoc 至少回答：

1. 该能力解决什么业务问题，由哪个领域拥有。
2. 调用前置条件、权限/租户/状态约束是什么。
3. 成功返回什么，幂等与重复调用如何处理。
4. 可能出现哪些业务失败，调用方是否可重试。
5. 是否产生事件、外部调用或其他可观察副作用。
6. 兼容性要求是什么；字段新增、枚举扩展和废弃如何演进。

## 4. 示例

```java
/**
 * 提交学员报名意图的公开能力，由报名领域拥有。
 */
public interface EnrollmentApi {

    /**
     * 创建一笔报名申请。同一幂等键重复提交时返回首次创建的申请，不重复扣减名额。
     *
     * @param command 报名意图，学员、班型和幂等键不能为空
     * @return 已创建或由幂等规则命中的报名结果，不返回 {@code null}
     * @throws EnrollmentRejectedException 学员状态或班型名额不满足报名规则时抛出
     */
    EnrollmentResult enroll(EnrollmentCommand command);
}
```

```java
/**
 * 报名命令，承载调用方已经确认的学员与班型选择。
 */
public final class EnrollmentCommand {

    /** 标识本次业务请求的幂等键，在调用方业务范围内唯一。 */
    private String requestId;

    /** 待报名学员 ID，必须对应有效且未注销的学员。 */
    private long studentId;
}
```

## 5. 审计与人工评审

先运行 `scripts/audit_java_modulith.py` 发现明显缺口，再执行项目实际的编译、Javadoc 构建和 Modulith 结构测试。脚本是基于源码形状的保守审计，不能判断注释是否真实准确；以下问题必须人工评审：

- 注释与当前业务规则是否一致。
- 是否用空话掩盖了单位、空值、状态和失败语义。
- 公开对象是否泄露了领域内部结构。
- 核心方法的事务、幂等和副作用说明是否与实现一致。
