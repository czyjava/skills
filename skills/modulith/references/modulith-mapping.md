# Modulith 代码映射与渐进迁移

Modulith 是领域边界的代码护栏，不是领域识别算法。先完成业务边界和依赖裁决，再映射代码结构。

## 映射原则

- 默认一个限界上下文映射为 `app` 下一个业务顶层包；是否独立 Maven module 由发布物边界决定，不由领域数量决定。
- 领域根包是公开能力面，放 `*Api / *Command / *Query / *Result / *Event` 等稳定契约。
- `application / infrastructure / infrastructure.dao` 等子包默认内部，不允许其他领域直接访问。
- 领域公开接口由本领域实现；消费领域不能在自己的包内定义对方能力接口，再要求对方实现。
- Action / Controller 只依赖领域公开面，不访问领域内部 Service、Dao 或 Entity。
- 表、缓存主记录和对象索引必须有唯一写入所有者；其他领域通过公开查询、只读投影或事件副本使用。
- 单个业务事务默认收敛在一个领域。跨域一致性明确同步失败、幂等、事件投递、补偿和最终一致责任。
- 稳定跨域流程可以成为流程域；临时用例编排留在拥有业务目标的领域，不建全局 `application`。
- 外部系统适配器进入使用它的领域 `infrastructure`；只有无业务语义的技术封装才进入工程公共模块。
- 业务领域地图中的基础域不自动映射为固定 `foundation` 包。先使用业务名称建模，再按目标项目工程约定落包。

## simple-modulith 最小映射

使用木仓后端工程骨架时，确认后的业务领域通常映射为：

```text
cn.mucang.<project>.<domain>                     领域公开面
cn.mucang.<project>.<domain>.application         用例编排、事务、能力实现
cn.mucang.<project>.<domain>.infrastructure      外部系统和技术适配
cn.mucang.<project>.<domain>.infrastructure.dao  本领域数据访问
```

工程入口和公共模块按 `mc-backend-blueprint` 处理。不能因为项目预设了 `action / boot / common / foundation`，就把它们画成业务领域，或把实际的业务基础域塞进这些通用包。

结构约束最少覆盖：

```java
ApplicationModules.of(ProjectModulith.class).verify();
```

- 模块无循环依赖。
- 跨模块只能访问根包公开类型或明确的 `@NamedInterface`。
- `allowedDependencies` 与业务依赖方向一致，并尽量收紧。
- 内部包不能被其他模块访问。
- OPEN 技术模块不能成为绕过业务边界的中转站。

具体注解和工程版本以目标项目当前依赖、已验证源码行为及 `mc-backend-blueprint` 为准，不凭其他项目经验假设。

## 当前与目标映射

先做差异表，不直接移动代码：

| 当前包 / 模块 | 当前职责事实 | 目标领域 | 目标公开面 | 数据所有权变化 | 依赖变化 | 迁移方式 |
|---|---|---|---|---|---|---|
| 旧结构 | 已验证行为 | 目标上下文 | API / Event | 保持 / 迁移 | 移除 / 新增 | 原地收口 / 适配 / 搬迁 |

同一旧包可能拆到多个领域；多个旧包也可能合并到一个领域。不能追求目录一一对应。

## 跨域契约

公开面只暴露领域外需要依赖的业务能力：

- `Command`：写动作意图，不复用 HTTP Req 或外部协议对象。
- `Query`：稳定查询条件，不泄漏 Dao Query。
- `Result`：领域结果，不直接返回 DO / Entity / 缓存行。
- `Event`：已经发生的领域事实，包含稳定身份和幂等所需信息。
- `@NamedInterface`：确有多个稳定公开面时使用，不为绕开内部包保护而滥用。

历史 JSON、外部回调、旧表扩展字段和供应商响应应在拥有来源语义的一侧转换。例如“外部执行结果 -> 稳定媒体快照 -> 业务结果投影”应分段建模，不让媒体领域理解生成领域的历史 payload。

## 数据所有权迁移

1. 先标记每张表、主记录、流水、缓存和对象索引的当前读写方。
2. 为目标领域确定唯一写入所有者和生命周期责任。
3. 其他领域先停止新增直连，通过兼容 API 或只读适配器收口访问。
4. 需要跨域读取时，选择公开查询、只读投影或领域事件副本，并说明一致性。
5. 完成双写、回填或切流后，删除旧写路径和临时兼容；不能无限保留双所有者。

## 渐进迁移顺序

推荐按可回证的小步推进：

1. **基线盘点**：锁定当前行为、调用图、表读写和测试结果。
2. **建立护栏**：引入 Modulith 入口、结构测试和当前允许依赖，先暴露真实违规。
3. **收口公开面**：建立领域 API / Event，把跨域内部包和 Dao 访问迁到契约后。
4. **明确所有权**：调整表、缓存和外部适配归属，处理事务、幂等与补偿。
5. **拆环与搬迁**：按依赖叶子到核心能力的顺序移动实现，保留最小兼容层。
6. **业务切流**：证明新路径已接入真实入口，不以“类已创建”代替完成。
7. **清理兼容**：删除旧入口、重复模型、临时事件、双写和放宽的依赖声明。
8. **运行回证**：验证关键业务、日志、数据和部署版本，记录未解决阻塞。

每一步应能独立测试和回滚。不要把领域拆分、数据迁移、接口破坏性升级和基础设施更换捆成一次大爆炸改造。

## 评审重点

- 目标 package 是否来自业务边界，而不是现有目录美化。
- 公开能力是否由正确领域拥有并实现。
- 是否存在跨域访问内部 Service、Dao、Entity、表或缓存行。
- 依赖方向是否与业务 DAG 一致，是否通过 `common` / `foundation` 绕边界。
- 外部执行者和供应商是否被当成内部领域。
- 兼容适配器是否放在理解旧语义的一侧。
- 已创建结构是否真正接入业务链路，已知阻塞是否保留为一等结论。
