# 领域事件设计

## 1. 先裁决协作方式

| 方式 | 适用场景 | 关键约束 |
| --- | --- | --- |
| 同步领域 API | 调用方必须立即得到结果，且失败需要共同回滚或立即决策 | 只依赖公开契约，禁止访问内部包和私有表 |
| 进程内领域事件 | 同一应用内，一个已经发生的业务事实触发多个相对独立的后续动作 | 明确事务提交前后；消费者失败不能被静默吞掉 |
| 可靠跨服务事件 | 跨进程协作、允许最终一致、需要重试与可追踪投递 | 需要稳定事件契约、幂等消费、重试和死信/补偿 |
| 低可靠通知 | 指标刷新、缓存失效等允许丢失且可重建的旁路动作 | 必须明确允许丢失，不能承载关键状态变更 |

能用明确同步结果完成的单一步骤，不为“解耦”强行改成事件；已经发生且存在多个独立后续动作的事实，不用反向 RPC 模拟广播。

## 2. 事件所有权与命名

- 事件由发生业务事实的领域定义并发布，消费者不能在自己的包里替发布方定义同名事件。
- 事件名使用过去式业务事实，如 `EnrollmentSubmitted`，不要使用 `HandleEnrollment` 这类命令式名称。
- 事件只携带消费者理解事实所需的稳定信息；敏感数据和聚合内部对象不得直接放入事件。
- 每个事件至少明确 `eventId`、业务主体标识、发生时间、事件版本和必要的追踪标识。
- 事件字段 Javadoc 按公开 POJO 标准说明单位、空值、枚举扩展和兼容语义。

## 3. 事务时机

- 需要观察已提交状态的消费者，应在事务提交后触发；不得在主事务未提交时让异步消费者读取未落库状态。
- 发布与业务落库必须说明一致性策略：同事务、本地消息表/Outbox、框架可靠投递或可接受的补偿窗口。
- 提交后发送失败不能伪装成业务事务成功即“全部完成”；要有待投递记录、重试或人工补偿入口。
- 消费者不得通过延时猜测上游是否提交完成。

木仓项目可优先核对 Golf XEvent 与目标项目已接入组件：本地 Spring 事件适合进程内协作，可靠跨服务事件优先使用项目验证过的 MQ/ONS 路径，允许丢失的旁路通知才考虑低可靠通道。具体依赖、路由和版本以目标工程源码为准。

## 4. 消费可靠性

- 消费者必须定义幂等键和去重范围，重复投递不得重复产生业务结果。
- 区分可重试异常、不可重试业务拒绝和数据契约错误；不能对所有异常无限重试。
- 明确最大重试次数、退避策略、死信/失败记录、告警和人工补偿责任人。
- 跨域最终一致流程要能回答：哪个状态是事实源，失败停在哪一步，如何恢复，恢复后是否会重复执行。
- 日志至少包含事件类型、事件 ID、业务主体标识、消费结果和追踪标识；不得记录完整敏感载荷。

## 5. 兼容演进

- 优先做向后兼容的字段新增；消费者必须容忍未知枚举和暂时不关心的字段。
- 删除、改名或改变字段语义时提升事件版本，并给出双写/双读或迁移窗口。
- 不复用旧事件名表达新的业务事实。
- Spec 和迁移 Plan 中记录发布方、消费者、版本、灰度顺序、回滚条件和存量消息处理方式。

## 6. 验证清单

- 发布时机与事务策略有自动化测试或可复现验证。
- 重复投递、乱序、延迟、消费者超时和永久失败均有测试。
- 事件 Javadoc、契约样例和真实序列化字段一致。
- 监控能区分发布失败、积压、重试、死信和业务拒绝。
- 运行态流程图单独表达 MQ、Worker 和外部服务，不把它们画成业务领域。
