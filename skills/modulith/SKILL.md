# Modulith 服务端蓝图

本技能回答“服务端应该有哪些业务领域、各自拥有什么、如何协作，以及怎样映射为可验证的 Modulith”。

## 职责边界

- 本技能负责业务领域识别、边界裁决、依赖设计、Modulith 映射和演进规划。
- 项目骨架、Maven module、SDK、组件接入和工程施工标准不在本技能范围内，遵循目标项目当前 `AGENTS.md`、README 和已验证工程事实。
- Spec、Validation、Plan 等文档的命名和治理遵循目标项目约定；没有专项约定时，使用本技能提供的蓝图模板和真相源拆分建议。
- 部署拓扑、进程、消息队列、Worker、对象存储、供应商和模型服务等运行态设计单独形成运行架构，不混入业务领域 DAG。

## 默认裁决

- 先盘点当前代码、表、接口、事件、配置和测试已经落地什么，再讨论目标领域；明确区分“当前事实、目标设计、迁移步骤、未决问题”。
- 不从 Maven module、Java package、类名或现有调用关系直接反推业务领域。代码结构是证据，不是领域真相本身。
- 判断一个能力是否值得独立成域，重点看业务语言与目标、规则与不变量、状态演进、数据所有权、事务与失败边界、公开能力和独立演进需求。
- “被核心能力依赖”“多处复用”“代码上已经独立”都不能单独证明它是支撑域或独立领域。
- 业务领域 DAG 只放业务域和真实限界上下文。产品入口可以作为图外调用方标注；Task Manager、Worker、MQ、对象存储、供应商和模型服务属于运行架构或外部系统契约。
- 不把场景、模板、编排、生产过程、媒体资产、商业化、运营配置等有独立业务语义的能力，为了图简单而压进一个大域。
- 领域能力由拥有该业务语义和不变量的领域定义并实现；其他领域通过公开契约协作，不在调用方定义接口再让拥有方实现。
- 历史格式、外部协议和供应商响应先由边界适配器翻译成稳定领域对象，接收方领域不理解上游内部格式。
- 业务基础域是领域分析结论，不等于代码里的固定 `foundation` 包；`common / foundation / action / boot` 等工程包不能替代业务建模。
- 领域结论必须同时给出图和术语映射表。图表达关系，表说明每个节点的边界、所有权和公开能力。
- Modulith 映射在领域边界确认之后进行；不能为了满足现有 package 形状而扭曲领域结论。

## 何时使用

- 为新服务规划业务域、限界上下文和依赖方向。
- 拆分巨型业务域、合并伪领域或澄清跨域能力归属。
- 把存量 Spring Boot 服务迁移为 simple-modulith / Spring Modulith 风格结构。
- 评审领域 DAG、模块公开面、表所有权、跨域调用、事件协作和循环依赖。
- 在需求开发前判断新能力应进入哪个领域，是否需要新增领域或流程域。
- 复盘“文档设计得很好，但代码实际落地到哪一步”这类领域建设状态。

## 执行流程

1. 明确本轮是新建、演进、迁移还是评审，以及目标服务、业务范围和不做事项。
2. 按 `references/evidence-and-domain-identification.md` 盘点现状证据，形成当前能力和所有权清单。
3. 基于统一语言、规则、不变量、状态、数据、事务和失败边界识别候选限界上下文，逐项给出拆分或合并理由。
4. 按 `references/business-domain-map.md` 产出业务领域地图、业务领域 DAG、术语映射和域外对象清单。
5. 明确每个领域的公开能力、数据所有权、事务边界、同步调用、领域事件和兼容适配责任。
6. 按 `references/modulith-mapping.md` 把确认后的领域映射到顶层包、公开面、内部包和允许依赖，并规划渐进迁移。
7. 使用 `assets/backend-domain-blueprint-template.md` 组织结果，按 `references/delivery-and-validation.md` 完成文档沉淀和验证。

## 最小交付物

- 当前事实清单：已落地能力、已接入业务链路、仅有代码但未接入的能力、已知阻塞和证据位置。
- 统一语言表：业务术语、准确含义、所属领域、易混淆词和禁用歧义。
- 领域目录：每个领域的目标、范围、公开能力、规则/状态、数据、事务/失败边界、依赖和不纳入范围。
- 业务领域 DAG：箭头方向和语义明确，且不包含运行时执行者或基础设施节点。
- 域外对象清单：需要进入运行架构、接口契约或 Ops 文档的系统和角色。
- Modulith 映射：当前结构与目标结构、顶层包、公开面、内部包、允许依赖和迁移顺序。
- 验证方案：结构测试、能力归属、禁止依赖、表所有权、行为回归和运行态回证。

## 推进原则

- 证据不完整时先继续读取可获得的代码和资料；不能安全确定的结论标为“候选 / 待确认”，不伪装成既定事实。
- 若某个业务定义会实质改变能力或数据所有权，且无法从现有真相源判断，再向用户澄清。
- 存量系统优先渐进迁移：先建立边界和测试护栏，再移动实现和数据访问，避免一次性重写。

## 禁止事项

- 不用“横向复用”“被核心域依赖”作为领域分类的充分条件。
- 不把 Controller、Action、Service、Dao、SDK、Worker 或供应商当成业务领域。
- 不把业务 DAG、上下文协作图和运行架构图揉成一张无法裁决的总图。
- 不只画方框，不说明业务语言、能力归属、数据所有权和依赖语义。
- 不把所有跨域编排塞进全局 `application`、`common` 或 `foundation`。
- 不让一个领域直接访问另一个领域的 Dao、Entity、内部子包或私有表。
- 不用未来设计覆盖当前事实，也不把已创建但未接入业务链路的代码描述为已经完成。
- 不隐藏循环依赖、临时兼容、外部阻塞和无法验证的结论。
